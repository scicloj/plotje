34  Architecture

Plotje has a five-stage pipeline: a pose becomes a draft, then a plan, a membrane, and finally a plot. Each stage is produced from the previous one by a single step. The user-facing functions pj/draft, pj/plan, and pj/plot are literal compositions of those steps, with pj/options folded in to inject pose-level options. Because the API is built as a composition, you can inspect each intermediate value and test each transition on its own.

This chapter introduces the single-step transitions, walks a small example through every stage, shows the user-facing functions as compositions, and explains how composite poses traverse the same pipeline through internal shape dispatch.

Pipeline Overview

Two terms used throughout: data space is values in their original units (centimeters, dollars, dates, species names); drawing space is the drawing-unit coordinates inside the output canvas. The plan stage holds geometry in data space; the membrane stage holds geometry in drawing space.

The five stages:

  • Pose – the composable specification you write. Built by pj/pose, pj/lay-*, pj/options, pj/facet, pj/arrange, pj/scale, and pj/coord. Lifted from raw data by pj/->pose, so a dataset can flow through the pipeline without an explicit constructor call. No computation has happened yet.

  • Draft – the pose flattened. A LeafDraft record holds :layers (a vector of one map per applicable layer with all scope merged in – :data, :x, :y, :mark, :stat, and aesthetic keys) and :opts (the pose-level options that flow into the plan stage). A composite pose, a leaf with a facet over columns, which is drawn as one cell per column, and a leaf whose facet is wrapped into rows with {:cols n} produce a CompositeDraft instead, carrying per-leaf drafts (:sub-drafts), the resolved composite-framing geometry (:chrome-spec), the layout map from leaf path to rect (:layout), and the composite’s overall dimensions (:width, :height). A leaf draft holds no geometry. A composite draft already holds where each cell sits on the canvas, in drawing units, because the sizes of the cells are decided before the cells are planned. Produced by pj/pose->draft.

  • Plan – fully resolved geometry in data space (domains, ticks, legends, computed shapes), and the layout of the canvas in drawing units. A Plan record (composite plots use CompositePlan) holding panels as plain maps, layers as PlanLayer records, and numeric arrays as dtype-next buffers. Produced by pj/draft->plan. No rendering primitives yet.

  • Membrane – a PlotjeMembrane record carrying positioned drawing primitives (Translate, WithColor, Path, Label, …) in drawing space, sized to the output canvas. The record itself implements the Membrane library’s UI protocols, so it composes with other Membrane elements. Produced by pj/plan->membrane. The Membranes chapter walks this stage in depth.

  • Plot – rendered output (SVG hiccup or BufferedImage). Produced by pj/membrane->plot, dispatching on a :format keyword.

The composition shortcuts pj/draft, pj/plan, pj/membrane, and pj/plot run the chain from a pose up through the named stage. They are introduced one section down.

Most users only interact with the pose stage and never need to think about the others. The stages below matter when you are debugging unexpected output, building a custom renderer, or extending the library.

Why these stages?

A simpler library could go from data to a rendered image in one function. Plotje splits the work into five stages so each stage addresses a distinct concern, and each boundary between stages has a specific purpose:

  • The pose is what the user specifies.

  • The draft is the same specification flattened, with scope merged in. This boundary lets the layer engine run on a uniform input regardless of how the pose was built (single layer, faceted leaf, composite tree).

  • The plan holds geometry in data space – domains, ticks, computed shapes – before any drawing. This boundary lets you inspect and validate plot structure with Malli, and it lets multiple renderers share the same computed plan. It also carries the dimensions the layout settled on, so where each panel will sit on the canvas is decided here: pj/frames reports it, and the membrane stage draws into it.

  • The membrane holds drawing primitives in drawing space. This boundary decouples “what to draw, where” from the output format, so SVG and raster renderers consume the same membrane tree.

  • The plot is the format-specific output: SVG hiccup, a BufferedImage, or any other format a backend supports.

Every intermediate value can be inspected with kind/pprint. The same pipeline can be extended by registering new methods at any stage – mark, stat, scale, coordinate system, output format – without modifying the core. The Extensibility chapter walks each extension point.

The Single-Step Transitions

Each transition is its own public function. Walk the example below to see what enters and what leaves at each step. The per-function reference (arities, arguments, return types) lives in the API Reference.

Step 1: pj/->pose

Lift raw data (or a pose) to a pose. Polymorphic on input: a dataset becomes a leaf pose with :data set; an existing pose flows through unchanged (idempotent). This is the structural lift that lets every downstream function accept either raw data or a pose. It stops there – it sets no mapping. The default mapping that makes a bare dataset render is filled in when the pose is drafted, and pj/infer-mapping writes it onto the pose ahead of that (see “Where Inference Happens” below).

The example traced through every stage is iris petal measurements, with a scatter and per-species regression line. Pose-level :x, :y, and :color mappings; two layers on top of that mapping.

(def trace-pose
  (-> (rdatasets/datasets-iris)
      (pj/pose :petal-length :petal-width {:color :species})
      pj/lay-point
      (pj/lay-smooth {:stat :linear-model})))

Step 2: pj/pose->draft

Flatten a pose into a draft. For a leaf, returns a LeafDraft record carrying the merged layer maps and the pose-level options. The pose-level mapping (:x :petal-length, :y :petal-width, :color :species) appears inside each of the two layer maps, alongside layer-specific keys (:mark, :stat). The layer engine downstream receives a uniform shape regardless of where each mapping was originally specified. Keys prefixed with double underscores (e.g. :__panel-idx) are internal markers; they pass through the plan stage and follow the Clojure “do not consume” convention.

A draft layer’s :data carries one column the pose was not given: :scicloj.plotje/row, the row of the pose’s dataset each row came from. A facet splits the data and a series pivots it, and either numbers the resulting rows from zero again, so the row number is attached before both. :brush true reads it, which is how highlighting a point in one panel highlights the same row in the others. Like the double-underscore keys, the column is Plotje’s: no mapping can name it, and no list of available columns shows it.

(def trace-draft
  (pj/pose->draft trace-pose))

Step 3: pj/draft->plan

Resolve the draft into computed geometry. Reads :opts from the draft to apply title, dimensions, axis labels, and so on. The smooth layer’s :linear-model stat resolves into per-species line segments here; the point layer keeps the raw observations grouped by species. The legend gets one entry per species.

(def trace-plan
  (pj/draft->plan trace-draft))

Step 4: pj/plan->membrane

Convert the plan into a PlotjeMembrane – a tree of membrane drawing primitives positioned in drawing-space coordinates, wrapped in a record that itself implements the Membrane UI protocols (IOrigin, IBounds, IChildren).

(def trace-membrane (pj/plan->membrane trace-plan))

The membrane carries the drawables plus the canvas size and title. The record fields :width and :height give the canvas size, the size the plan settled on, and :plotje/title carries the title when one is set. This plot sets none:

(select-keys trace-membrane [:width :height :plotje/title])
{:width 600, :height 400}

Step 5: pj/membrane->plot

Convert the membrane into the rendered output for a chosen format. Dispatches on the format keyword. This is the only stage whose output is format-native rather than portable: every earlier stage is the same across backends, while here the membrane becomes SVG hiccup, a BufferedImage, or another format’s bytes. The membrane carries its plan-derived dimensions as record fields (read via (membrane.ui/width m)/(height m)), so pj/membrane->plot does not need them written again in its options:

(def trace-plot

Pipeline Shortcuts: pj/pose, pj/draft, pj/plan, pj/membrane, pj/plot, pj/save

Each pipeline stage has a user-facing convenience that runs the chain from raw input up through that stage; pj/save is the file-output sibling that runs the chain all the way and writes the result to disk:

  • pj/pose – not a literal composition. On raw data its one-argument form is pj/->pose. With more arguments it reads column arguments ((pj/pose data :x :y)) and a mapping, and on an existing pose it merges them into that pose’s mapping. It infers nothing: the default mapping is filled in when the pose is drafted.

  • pj/draft – from raw input to a draft.

  • pj/plan – from raw input to a plan.

  • pj/membrane – from raw input to a membrane tree.

  • pj/plot – from raw input to a rendered figure.

  • pj/save – from raw input to a file on disk (renders, then writes).

pj/draft->membrane and pj/draft->plot start the same chain from a draft rather than from raw input.

Each shortcut starts from raw input and stops at a different stage along the same chain. The solid line is the stage-to-stage pipeline; each dashed arrow is one shortcut, running from raw input up to the stage it produces:

The shortcuts from pj/draft on are near-literal compositions of these steps: each lifts raw input with pj/->pose, applies the shared pj/infer-mapping step (which gives a pose that names no :x or :y column the default mapping of its data, and changes nothing on a pose whose mapping names one), and runs the chain up to its stage. Their source shows the pipeline directly. Two things are simplified below for clarity: the pj/->pose caller-name argument – which only tunes error messages – is elided, and pj/pose is shown at its 1-arity (its other arities also read column arguments and a mapping).

Pseudocode:

(defn pose         ; 1-arity; the other arities also read
  ([x]             ; column arguments and a mapping
   (-> x
       ->pose)))

(defn draft
  ([x]
   (-> x
       ->pose
       infer-mapping
       pose->draft))
  ([x opts]
   (-> x
       ->pose
       (options opts)
       draft)))

(defn plan
  ([x]
   (-> x
       ->pose
       infer-mapping
       pose->draft
       draft->plan))
  ([x opts]
   (-> x
       ->pose
       (options opts)
       plan)))

(defn membrane
  ([x]
   (let [pose (-> x
                  ->pose
                  infer-mapping)
         opts (:opts pose {})]
     (-> pose
         pose->draft
         draft->plan
         (plan->membrane opts))))
  ([x opts]
   (-> x
       ->pose
       (options opts)
       membrane)))

(defn plot
  ([x]
   (let [pose (-> x
                  ->pose
                  infer-mapping)
         opts (:opts pose {})
         fmt  (or (:format opts) :svg)]
     (-> pose
         pose->draft
         draft->plan
         (plan->membrane opts)
         (membrane->plot fmt opts))))
  ([x opts]
   (-> x
       ->pose
       (options opts)
       plot)))

(defn save
  ([x path] (save x path nil))
  ([x path opts]
   (let [pose (-> x
                  ->pose
                  infer-mapping)
         pose (if opts (options pose opts) pose)
         fmt  (resolve-format pose path)]  ; :format opt, else path extension
     ;; render the plan to fmt bytes, write them to path,
     ;; and return the java.io.File written
     (write-file path (plan->plot (plan pose) fmt (:opts pose))))))

In plot, the let binds pose, opts, and fmt for use in the subsequent -> thread, which runs the four transitions (pose->draft, draft->plan, plan->membrane, membrane->plot) in order. The membrane carries the dimensions the plan settled on as record fields, and the title under :plotje/title, so membrane->plot reads them without the plan.

pj/save is the file-output sibling: it lifts and infers the same way, resolves the file format (from a :format option or the path extension), renders the plan to those bytes, and writes them to disk, returning the file it wrote as a java.io.File (str of it is the path). resolve-format and write-file above stand in for that format-resolution and file-writing detail.

The 2-arity of each function folds the options map into the pose using pj/options before recursing into the 1-arity.

pj/membrane is the analogous shortcut for the membrane stage, useful for a caller that needs a membrane tree without choosing an output format yet – for example a custom backend, or a target that Membrane supports but Plotje has not wired in yet.

Because the compositions call the steps, redefining a step with with-redefs takes effect in pj/draft, pj/plan, pj/membrane and pj/plot. pj/save calls the render multimethods without going through the public step functions, so a with-redefs of pj/plan->membrane does not reach it.

The same property allows inspection at any stage: stop the chain before the next step. (-> data ... pj/pose->draft kind/pprint) shows the draft; (-> data ... pj/pose->draft pj/draft->plan) shows the plan.

Where Inference Happens

Two of the steps also infer: they fill in choices the user did not specify. Inference is what lets a dataset alone – with no mapping, no layers, no options – produce a complete plot. Most one-line examples in this book rely on inference at one or both of these stages. The Inference Rules chapter is the authoritative reference for what each stage infers.

(pj/pose {:x [1 2 3 4 5]
          :y [2 4 3 5 4]
          :g [:a :a :b :b :b]})

Where each kind of inference lives:

  • Mapping inference fills in :x, :y and :color on data of one to three columns: one column to :x, two columns to :x and :y, and a third column to :color. It runs in pj/pose->draft, after a facet over columns is expanded into cells, on every leaf, cells of a composite included. It writes the default in two cases: where no mapping and no layer names an :x or a :y column, and where the first layer names no column, whatever later layers name (the example below this list shows a later layer naming the default’s columns). Where a layer names :y alone and its layer type draws from two columns, :x is filled in with the first column nothing names, so (pj/lay-point data {:y :b}) draws :b against :a. pj/infer-mapping is the same step as a public function: it writes the default onto the pose, where it can be read before drafting. pj/->pose, pj/pose and the pj/lay-* functions read no column of the data when they are called: a layer naming no column is given its columns when the pose is drafted, and a layer left without a column is reported then.

  • Layer-type inference is written into the draft. A pose with no pj/lay-* call is given one layer, of the type its columns choose: a categorical x with a numerical y gives a boxplot, a temporal x with a numerical y gives a line, a numerical x and y give a scatter, and one numerical column gives a histogram. pose/elaborate makes the choice, so the draft layer already holds its :mark and :stat. pj/draft->plan chooses the stat of a layer whose type leaves it open – a bar with no :y column counts – and gives a draft layer written by hand with no :mark the type its columns choose.

  • Column-type inference lives in pj/draft->plan. :x-type/:y-type/:color-type default from the data (numerical / categorical / temporal); a user-supplied :x-type overrides the default.

  • Geometry inference lives in pj/draft->plan. Domains default to data ranges; ticks default to evenly-spaced values; legend entries are derived from the layers’ aesthetic mappings; the coordinate system defaults to :cartesian.

Mapping inference and the choice of a layer type run in pj/pose->draft; the rest runs in pj/draft->plan. Every inferred default has an explicit override (pj/scale, pj/coord, pj/options, mapping keys like :x-type), so the user can opt out of any single inference without losing the others.

Below, pj/pose->draft gives a pose built by pj/->pose the default mapping of its three columns, with no pj/infer-mapping call in between. The points keep the color of the default beside a smooth that names the default’s :x and :y columns:

(->> (-> {:a [1 2 3 4] :b [2 4 3 5] :c ["u" "u" "v" "v"]}
         pj/->pose
         pj/lay-point
         (pj/lay-smooth :a :b)
         pj/pose->draft)
     :layers
     (mapv #(select-keys % [:mark :x :y :color])))
[{:mark :point, :x :a, :y :b, :color :c}
 {:mark :line, :x :a, :y :b, :color :c}]

What elaboration writes

Before it flattens a pose, pj/pose->draft writes into the pose what the draft would otherwise have to choose, in this order: the rows the pose keeps (its :where); a series pivoted into a key column and a value column; the default mapping of data with one to three columns; one layer, where the pose names columns and has no layer; the panel’s columns, into each layer that reads them; a layer type for each layer left to inference; and the flip of a column named on :y alone. The function that does this is pose/elaborate. Panels shows which of the panel’s columns a layer reads, and Layer Types shows the flip.

Where the layers of a panel draw different columns and no layer is colored by a column, pj/pose->draft also gives each layer that specifies no :color a color and a legend entry naming its columns, as Panels shows.

The composite path also performs work across leaves that a single leaf has no counterpart for: deciding which cells share an axis, and what that axis covers. The next section follows it through the stages.

How Panels Share an Axis

Panels that are meant to be compared are drawn on one axis: the same numbers, or the same categories, in every panel. Plotje draws several panels in two ways, and both follow one rule: a shared axis covers what the panels sharing it draw.

  • A facet by categories – the categories of one column in one row, or a grid crossing the categories of two columns under :col and :row – is one plan with several panels.

  • An arrangement, a facet over columns, and a facet wrapped into rows with {:cols n} are each a CompositePlan: one plan per cell.

The pose stage decides which cells share

pj/pose->draft reads the composite’s :share-scales and puts the cells into groups. It measures no extent to do this. It reads the type of each column, to report cells that cannot share, and for a column of categories the order the data holds them in, which the group carries as :order. Each sub-draft carries the groups of its cell under :share, by axis:

(->> arranged-clinics
     pj/draft
     :sub-drafts
     (mapv :share))
[{:y {:group 0}} {:y {:group 0}}]

Two cells are placed in one group where they draw the same thing along an axis: the values of one column, or what a stat computes from one column – a count, a density – which the stat declares (see What a stat computes). A count of a column and the values of that column are never in one group. Which axes are shared by default, and the other values :share-scales takes, are in Composition.

The plan stage decides what the axis covers

What a cell draws is known only after its stats have run. A stack of bars reaches the sum of its parts, which no row of the :visits column holds. So pj/draft->plan first measures every sharing cell: plan/draft->extents runs the cell’s stats and returns the extent the cell draws on each axis, before any padding.

(->> arranged-clinics
     pj/draft
     :sub-drafts
     (mapv (fn [sub-draft]
             (plan/draft->extents (:draft sub-draft) (:opts sub-draft)))))
[{:x ["w1" "w2"], :y [0.0 50.0]} {:x ["w1" "w2"], :y [0.0 105.0]}]

The extents of a group are pooled: numbers by the lowest low and the highest high, categories by listing every category of every cell. Each cell is then planned with the pooled extent in place of its own. The pooled extent is in the cell’s options in the plan:

(->> arranged-clinics
     pj/plan
     :sub-plots
     (mapv (fn [sub-plot] (:y-scale-domain (:opts sub-plot)))))
[[0.0 105.0] [0.0 105.0]]

Every cell pads that one extent the same way, so the panels end on one domain:

(->> arranged-clinics
     pj/plan
     :sub-plots
     (mapv (fn [sub-plot] (:y-domain (first (:panels (:plan sub-plot)))))))
[[0.0 110.25] [0.0 110.25]]

Two details complete the grouping. A cell whose layers draw two columns on an axis belongs to the groups of both columns, and the two groups become one: three cells sharing :y, drawing :adults, :children, and both, are one group. And a cell’s numeric domain is widened after planning so that its text marks are drawn in full; cells of a group that end on different domains are planned again with the widest domain as a floor, so that they agree.

A sharing cell’s stats run twice: once to measure it, and once to plan it with the pooled extent. A cell that shares with no other cell is not measured.

A facet in one plan follows the same steps inside pj/draft->plan: its panels are measured without padding, pooled, and each panel is then given the pooled extent and padded. The facet of the two clinics ends on the domain the arrangement ends on:

(->> faceted-clinics
     pj/plan
     :panels
     (mapv :y-domain))
[[0.0 110.25] [0.0 110.25]]

Poses rewritten before drafting

Some poses are rewritten into the cells they stand for before any of the above runs, so that one spelling cannot be drawn differently from another. pj/pose->draft does this in pose/expand-facet-nodes.

A facet over columns is kept on the pose as written, and expanded into a composite of one cell per column. A series faceted by the key column the series pivot adds asks for the same panels, so it is first rewritten into a facet over the columns of the series, and then expanded like any other, here on weekly counts of visits:

(def weekly-visits
  {:week [1 2 3 4]
   :adults [30 25 28 35]
   :children [20 15 18 22]})
(def series-by-key
  (-> weekly-visits
      (pj/lay-line :week [:adults :children])
      (pj/facet :series)))

From here the pose is an ordinary composite: its cells are grouped, measured and planned as the two clinics above were. Cells that split the data of one pose share by default each axis on which they draw one column. In the series faceted by its key, each cell draws a column of its own on :y, so the two cells share :x and not :y:

     :sub-drafts

[{:x {:group 0}} {:x {:group 0}}]

Cells written by hand, each keeping the rows of one value of a column with :where, that together keep every value of the column are rewritten the other way, into one pose faceted by that column (pose/collapse-regular-split).

Where a Mistake Is Reported

When a pose cannot be drawn, which step reports the error depends on what the error depends on. A call reports what its own arguments decide. pj/pose->draft reports what depends on which columns the data has, and on how the layers of a panel or the cells of a facet relate. pj/draft->plan reports what is known once a layer’s stat and mark meet the values of its columns – a bar given two categorical columns, a mark polar coordinates have no drawing for – and panels too small for the canvas. So pj/lay-point naming a column the data lacks returns a pose, and drafting that pose reports the column.

The table below builds a pose for each mistake and runs the steps in order. It shows the first step that reports an error, and the first sentence of the message:
